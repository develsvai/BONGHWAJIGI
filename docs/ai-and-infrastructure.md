# AI 역할과 서버 구성

현재 설계 검토의 하드웨어 기준은 대화에서 확인한 **NVIDIA L4 24GB, 4 vCPU, RAM 48GB**입니다. 이 규모에서 한 지역·한 재난 유형의 MVP 모델 구성을 검토할 수 있습니다. 아래 후보 모델의 실제 처리량, 지연, 동시 실행 메모리는 아직 이 구성으로 측정하지 않았습니다.

## AI 역할 경계

사용자는 AI의 임의 판단을 금지한다고 명확히 했습니다. 회의 00:48:44~00:49:44에는 LLM을 사용자 전달 문장 생성에만 사용하고 데이터 선별·추론에 사용하지 않겠다는 더 구체적인 제한이 있습니다.

현재 문서에서는 이 제한을 기본선으로 보존합니다. LLM에 기사 사실 추출이나 자료 선택을 맡기는 이전 제안은 **확장 검토 항목**이며 기본 구현 요구로 확정하지 않습니다. 입력을 제한하거나 구조화된 출력 형식을 사용해도 내용의 사실성이 자동으로 보장되는 것은 아닙니다.

| 작업 | 처리 방안 | 상태 |
| --- | --- | --- |
| 공식 API 필드 읽기와 자료 검증 | 파서, 스키마·좌표·시각 검증, 출처·정정 규칙 | 설계 제안 |
| 사건 검색과 중복 후보 탐색 | 위치·시간·키워드 우선, 필요시 임베딩 검색 보조 | 임베딩 사용 범위 미결정 |
| 주변 지역의 물리적 영향 평가 | 재난별 관측·공간 관계와 검증된 모델·규칙 | 자료와 예측 대상 미결정 |
| 위험 확률 계산 | 별도 학습·검증한 통계 모델 | 모델 및 학습 자료 미결정 |
| 행동·대피 여부 선택 | 검토한 정책과 사용자 상태 비교 | 정책·임계값 미결정 |
| 근거와 선택된 행동 설명 | 승인된 안내 문구와 제한된 SLM 생성 | 회의 방향, 모델은 후보 |
| 음성 출력 | TTS 및 미리 생성한 공통 안내 | 요구사항 |

| 경로 탐색과 3D 표시 | 경로 알고리즘과 지도·공간 데이터 렌더링 | 구현 방식 미결정 |

## 모델 후보

| 후보 | 맡길 수 있는 역할 | 배치 제안 | 준비할 검증 |
| --- | --- | --- | --- |
| [Qwen3-4B-Instruct-2507](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507) | 선택된 대응과 근거의 짧은 설명 | GPU | 한국어 문장, 근거 일치, 행동 지침 변형 여부, 응답 시간 |
| [Qwen3-Embedding-0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B) | 관련 문서 검색과 중복 후보 탐색 | 허용 범위 확정 후 GPU 또는 CPU 검토 | 같은 사건 검색 성능, 서로 다른 사건 혼동, 출처 중복 |
| [XGBoost](https://xgboost.readthedocs.io/en/stable/gpu/index.html)와 [확률 보정](https://scikit-learn.org/stable/modules/calibration.html) | 정해진 사건·지역·시간 범위의 영향 평가 | 학습 시 GPU 선택, 운영 추론은 CPU 가능 | 사건 단위 평가, 누락·오탐, 확률 신뢰도, 정보 누출 |
| [MeloTTS-Korean](https://huggingface.co/myshell-ai/MeloTTS-Korean) | 한국어 안내 음성 | CPU 우선 검토, 필요한 경우 GPU | 지명·주소·숫자 발음, 실제 기기 청취, 생성 지연 |
| STT 모델 | 사용자의 이동 불가·지원 필요 응답 인식 | 음성 대화 포함 시 선정 | 소음·발음·말 끊김, 중요 응답의 확인 방식 |

Qwen3-4B-Instruct-2507은 사고 과정 블록을 출력하지 않는 버전이며, 설명을 짧게 생성하는 용도로 검토했습니다. 그 특성이 환각이나 잘못된 안내를 없애지는 않습니다. 긴급 행동은 검토한 템플릿으로 즉시 표시하고, 생성 설명은 선택된 내용과 근거를 벗어나지 않는지 검사하는 방안을 제안합니다.

임베딩은 문서 의미의 유사도를 제공합니다. 검색 점수를 사건의 사실 확률이나 재난 확산 확률로 사용하지 않습니다. Qwen 임베딩을 데이터 선별 보조에 사용하는 것이 회의의 제한에 부합하는지도 별도로 결정합니다.

MeloTTS는 공식 저장소에서 CPU 추론을 지원한다고 설명합니다. 실제 4 vCPU 환경에서 다른 작업과 함께 동작할 때의 지연은 확인해야 합니다. [MeloTTS 공식 저장소](https://github.com/myshell-ai/MeloTTS)

## 확률 모델을 준비하는 방법

XGBoost는 우리 지역의 위험을 이미 학습한 완성 모델이 아닙니다. 다음 순서로 목표와 데이터를 정해야 합니다.

1. 재난 종류, 평가할 공간 단위, 시간 범위, 실제 관측으로 판별할 결과를 정의합니다.
2. 해당 시점에 알 수 있었던 기관 자료, 기상·관측, 사건 정보와 실제 결과를 연결합니다.
3. 독립 출처, 거리·방향, 경과 시간, 재난별 관측값을 입력으로 구성합니다. 출처 수를 기계적으로 위험 증가 요인으로 삼지 않습니다.
4. 단순 규칙 또는 통계 기준 모델과 비교하고, 학습에 쓰지 않은 사건·시기에서 평가합니다.
5. 예측값이 실제 관측 빈도와 맞는지 확인하고 필요한 확률 보정을 수행합니다.
6. 검증 범위를 벗어나거나 자료가 부족하면 평가 불가 또는 위험 점수로 표시합니다.

같은 재난의 기사들이 학습과 평가 양쪽에 섞이거나, 나중에 나온 결과 보도를 과거 입력으로 쓰면 성능을 과대평가할 수 있습니다. 사건·시간 기준 분리와 발표 시각 기준 재현이 필요합니다.

새 관측이 들어오면 최신 입력으로 **재추론**합니다. 모델 **재학습**은 별도 검증과 버전 교체 절차로 수행합니다. 서로 다른 기관의 확률은 대상 사건·시간·공간·단위가 같은지 확인하기 전 단순 평균하지 않습니다.

실제 학습 자료가 없는 해커톤 데모는 규칙 기반 점수 또는 명시적인 시뮬레이션으로 표현하고, 검증된 발생 확률처럼 제시하지 않습니다.

## 서버와 모바일의 역할

| 위치 | 역할 제안 |
| --- | --- |
| 기존 K8s 클러스터 | 수집 일정, 큐, 정규화, DB, 공간 검색, 정책 적용, 알림, 경로 계산 |
| L4 GPU 서버 | SLM 추론, 허용 시 임베딩 추론, 별도 시간대의 모델 학습·평가 |
| CPU 작업 서비스 | 작은 확률 모델 추론, TTS 생성과 음성 캐시 |
| 모바일 클라이언트 | GPS·사용자 응답, 안내 표시, 지도·3D 렌더링, 음성 재생 |

GPU 서버를 K8s 노드로 편입할지, 별도 추론 API로 연결할지는 미결정입니다. 여러 프로세스가 GPU 메모리를 경쟁하지 않도록 실행 방식과 사용 한도를 정해야 합니다. GPU 서버의 4 vCPU에 수집·DB·모델 전처리까지 모두 몰지 않는 구성을 제안합니다.

4B와 0.6B 모델을 16비트로 올리면 가중치만 단순 계산해 약 8GB와 1.2GB입니다. 이 값은 실측 총사용량이 아니며 실행 버퍼와 캐시가 추가됩니다. 두 모델 병행은 임베딩 사용이 허용되는 경우의 후보 구성입니다. 입력 길이와 동시 처리 수를 제한해 24GB 내 실제 사용량을 확인해야 합니다.

처음에는 짧은 입력·출력, 사건 단위 결과 재사용, 공통 음성 사전 생성으로 검증합니다. 학습과 긴급 추론을 같은 GPU에서 동시에 돌리는 것은 초기 운영 구성에서 피하는 제안입니다.

## 경로와 3D

경로는 위험·통제·사용자 이동 제약을 반영한 그래프 탐색으로 계산하는 방안을 제안합니다. 지도 API가 계단·경사·재난 통제를 모두 제공한다고 가정하지 않습니다.

회의에서는 Unity 시연과 AI·Unity 개발 분리를 논의했습니다. [CesiumJS](https://cesium.com/platform/cesiumjs/)는 이후 검토한 웹 기반 3D 지도 대안입니다. 어느 쪽도 최종 선정되지 않았습니다.

일반적인 3D 경로 표시는 별도 생성 모델 대신 확보한 지도·지형·건물 데이터 위에 경로를 표시할 수 있습니다. 카메라 물체 인식, 정밀 실내 위치 추정, AR 안내는 별도 기술 범위이며 현재 GPU 구성이 그 전체 기능을 검증했다는 뜻은 아닙니다.

## 측정 후 결정할 사항

- 모델별 한국어 정확도, 지연, 메모리와 동시 실행 가능 범위
- 분당 유입 문서·사건 수, 사용자 매칭 수, 알림 집중 상황의 대기 시간
- 소스 발표부터 앱 표시까지 단계별 지연과 실패율
- 실제 경로 데이터의 계단·통제·대피 장소 정보 완전성
- 모바일 운영체제별 알림 권한, 백그라운드, 전체 화면·음량 제어 가능 범위

서버 용량 검토는 서비스의 예측 정확도나 실제 재난 대응 안전성을 입증하지 않습니다. 첫 구현 전에 데이터 접근과 검증 가능한 목표를 먼저 고정해야 합니다.
