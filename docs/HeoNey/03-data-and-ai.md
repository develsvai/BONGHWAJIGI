# 03. 데이터·AI·경로 구성

[문서 안내](README.md) · 근거: [M019–M020](archive/conversation-03.md#m019), [M045–M048](archive/conversation-06.md#m045), [M056](archive/conversation-07.md#m056)

## 사용자가 제시한 구성

M045에서 사용자는 재난 데이터와 경로 데이터가 필요하고, 한 번 수집한 자료로는 충분한 교차 확인이 어렵다고 설명했다. 기상청·국내 재난 기관·국제 재난 예측 자료를 수집하는 파이프라인, 분류모델, 예측을 반영한 경로 생성, 대피경로 데이터, 모바일 3D 경로와 실시간 안내를 구상했다. 이는 사용자가 밝힌 시나리오이며 연결이 검증된 시스템은 아니다.

원문에서 말한 “재난청”은 특정 API나 실제 기관을 확정한 표현으로 해석하지 않는다. 답변은 국내 공식 재난정보와 행정안전부 계열 공개 자료를 후보로 제시했다.

## 단계별 역할 분리

| 단계 | 역할 | 원문 답변에서 보완한 점 |
| --- | --- | --- |
| 수집 | 국내·국제 재난 자료를 반복적으로 가져옴 | 제공처별 갱신 주기·지연·장애 차이 고려 |
| 정규화 | 시간·지역·좌표·재난 종류 등 비교 기준 맞춤 | 같은 현상을 가리키는지 확인한 뒤 비교 |
| 출처 간 대조 | 관측·예측·공식 지시 사이의 일치·충돌 확인 | 기관 수만 늘린다고 동일 의미의 데이터가 되는 것은 아님 |
| 상황 분석 | 재난 유형·정보 충돌·대응 우선순위 분석 | 분류모델의 역할과 공식 지시를 구분 |
| 개인 상태 이해 | 음성에서 현재 이동·동반·지원 조건 추출 | 평소 프로필보다 현재 확인된 정보 우선 |
| 대응 방법 선정 | 가능한 이동 또는 지원 방안 선택 | 개인 맞춤 추천을 별도 단계로 유지 |
| 경로 탐색 | 확인된 도로망에서 제약에 맞는 후보 계산 | 생성모델이 실제 없는 길을 만들지 않도록 분리 |
| 3D 표현 | 선택된 경로·지형·건물을 모바일에 표시 | 렌더링과 경로의 안전성 판단은 별개 |
| 재안내 | 재난·통제·사용자 상태 변화 반영 | 상태 변경 시 추천 조건 재검토 |

“교차검증”은 학습 모델의 cross-validation과 여러 기관 자료를 비교하는 cross-source verification을 구별해야 한다는 답변이었다. 이 대화에서 필요로 한 핵심은 후자다.

## 원문에서 제시한 데이터·도구 후보

아래는 원문의 후보와 용도를 옮긴 표다. 현재 API 권한·응답·갱신 주기를 실측하거나 사용 승인을 받은 것은 아니다.

| 후보 | 원문에서의 용도 | 구현 전 확인할 점 |
| --- | --- | --- |
| [기상청 API허브](https://apihub.kma.go.kr/apiInfo.do) | 기상특보·강수·태풍·호우 자료 | API별 관측·예측 구분과 갱신 주기 |
| [재난안전데이터 공유플랫폼](https://www.safetydata.go.kr/) | 재난문자·공식 재난 상황·대피 지시 | 제공 데이터 종류, 위치 표현, 지연 |
| [생활안전지도 홍수범람위험도](https://www.safemap.go.kr/dvct/data/selectDataAPIDetail.do?dataApiId=6) | 침수 위험지역 참고 | 위험도 지도와 현재 침수 여부 구분 |
| [GloFAS](https://global-flood.emergency.copernicus.eu/) | 국제 하천 홍수 예측 참고 | 공간·시간 해상도와 국내 적용 범위 |
| [GDACS](https://www.gdacs.org/) | 국제 재난 상황과 비교 | 국내 세부 지역 자료와 비교 가능한 범위 |
| 공공 대피시설·도로·통제·지형 자료 | 시설 선택과 보행 가능한 경로 | 재난 유형 적합성, 운영 여부, 접근성, 최신 통제 |
| [CesiumJS](https://cesium.com/learn/cesiumjs-learn/) | 3D 지형·건물·경로 표현 | 모바일 성능, 데이터 이용 조건, 렌더링 범위 |

답변은 국제 예측 자료를 한국 골목길의 실시간 침수 판정으로 취급하지 말고 국내 공식 정보를 우선하는 보조 자료로 다룰 것을 제안했다. GloFAS의 범위에 대한 설명은 원문 주장으로서 [M046](archive/conversation-06.md#m046)과 [외부 출처 목록](references.md)에 보존했다.

## 경로 생성과 3D 표현

사용자는 생성모델과 “경로 데이터를 3D화하는 모델”을 언급했다. 답변은 경로 탐색 알고리즘으로 실제 도로망의 후보를 계산하고, 별도 3D 지도 기술로 표현하는 방향을 제안했다. 구체적인 3D 모델 이름이나 링크는 공유 대화에서 확인되지 않았다.

경로 후보에는 공식 통제·위험 구간, 계단 이용 제한, 이동거리 부담, 실제 이용 가능한 대피시설을 반영하는 안이 제시됐다. 정보가 없는 도로를 안전한 도로로 확정하지 않으며, 확인되지 않은 경우 경로 안내를 보류하는 분기가 포함됐다.

자료 연결의 핵심은 **위험지역, 실제 보행 가능한 도로망, 재난에 적합한 대피시설**의 세 축이다. 예쁜 3D 화면만으로 이 연결이 완성되는 것은 아니다.

## NVIDIA L4와 모델 후보의 맥락

사용자가 확실히 밝힌 자원은 해커톤에서 제공받는 **NVIDIA L4 GPU**다. GPU 수량, 실제 서버 접근 조건, 동시 사용자 수, 지연 목표는 이 공유 대화에서 확정되지 않았다.

초기 아동 정보보호 후보에서 PaddleOCR, 객체 탐지, Qwen2.5-VL 3B/7B, Whisper, OpenCV·FFmpeg가 언급됐다. 대형 모델을 처음부터 학습하기보다 사전학습 모델 추론을 활용한다는 제안이었다. 이를 그대로 재난 앱의 선정 기술 스택으로 기록하지 않는다.

재난 서비스에서의 제안 역할은 음성 인식, 사용자 표현 이해, 재난 공지의 쉬운 말 변환, 개인 조건 분석과 설명이다. 방언이나 고령자 발화, 복수 모델의 메모리 사용, 지연·동시성은 실제 데이터와 모델 선정 후 검증해야 한다는 맥락이다.

최신 음성 요구는 자동 인식과 발화 중 끼어들기이므로 실시간 음성 입력, 발화 감지, 음성 출력 중단, 스피커 음성 재인식 방지 등이 후속 구현 요소로 제안됐다. 특정 SDK나 모델 채택은 정해지지 않았다.

## 해커톤 구현 범위에 대한 제안

실시간 재난 자료의 수집·표시와 모의 재난에서 개인별 대피 결과를 비교하는 시연을 구분한다. 실제 수집 자료를 보여주더라도 모의 침수·도로 통제·대피 시나리오를 실제 현장 판단 결과처럼 표현하지 않는다.

초반 가정용 비서 구상에서는 정전·통신 두절·기기 고장과 대체 수단도 논의됐다. 모바일로 바뀐 이후의 구체적인 오프라인 동작·전원·알림 보장은 여전히 미결정이다.
