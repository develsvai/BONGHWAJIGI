# 산불 MVP 데이터 재검수 — 10분 갱신 기준

검수일: 2026-10-31 KST · 기존 35개 항목 전체 재분류 + 신규 후보 1개. 이 문서가 산불 MVP의 갱신 기준을 설명하는 최신 보완 문서다. 기존 전체 재난 카탈로그와 사례 파일은 당시 기록으로 보존한다.

## 먼저 결정할 기준

자료 담당자가 제안한 **주기가 확인된 자료 우선, 확인이 필요한 자료 차순위** 원칙을 적용한다. 단, 주기를 알더라도 1시간·3시간인 자료를 실시간 1순위로 올리지는 않는다.

| 판정 | 선정 조건 | 운영 전 확인할 사항 |
| --- | --- | --- |
| 1순위 | 공식 문서에 기관/API 갱신이 10분 이내로 명시되고 산불 용도에 맞음 | 승인키 성공 응답, 원본 시각, 실제 전달 지연 확인 필요 |
| 1순위·보완 | 대표 피드 주기는 충족하나 국내 산불 커버리지와 선택 제품 적용 범위가 제한됨 | 국내 산불 주탐지로 채택하지 않음 |
| 2순위 | 생산·관측 간격은 짧지만 API 공개 갱신 상한이 불명확하거나 ‘실시간/수시’만 표기 | 실제 응답을 일정 기간 저장하며 지연 측정 |
| 보조 | 알려진 시간 간격·지연이 10분을 넘거나 실시간 적합성이 입증되지 않은 과거·예보 자료 | 과거 학습, 장래 예보, 광역 보조 용도로 사용 |
| 기본자료 | 지형·임상·지도·대피시설 위치 등 정적 정보 | 최신 판본·좌표·범위를 확인하고 캐시. 10분 기준 적용 제외 |
| 보류 / 범위밖 | 통계와 실시간 설명 충돌 / 다른 재난 전용 | 설명 해소 전 실시간 후보 제외 / 확장 목록에 보존 |

**현재 운영에서 ‘항상 10분 안에 수신된다’고 검증된 소스는 없다.** 1순위는 연결 후보 선정 순위이며 운영 성능 보증이 아니다. 수치 지연을 모르면 `미검증`으로 남긴다. 아래 모든 순위는 이번 기준으로 다시 정한 것이며, 기존 P0/P1과 의미가 다르다.

## 기존 목록에서 달라진 점

- F01~F04 FIRMS는 한국 포함 전지구 NRT가 관측 후 3시간 이내 제공되므로 10분 실시간 핵심 입력에서 제외한다. 통과 대기시간도 추가된다. 미국·캐나다의 초고속 자료를 한국에도 적용할 수 있다고 해석하지 않는다. 기존 표본·지도 표시·광역 보완은 계속 유용하다. [NASA 공식 설명](https://firms.modaps.eosdis.nasa.gov/)
- D02 산림청 산불발생통계는 포털의 실시간 표기와 공식 설명의 분기 집계가 충돌한다. 따라서 ‘측정하면 될 것 같은 실시간 산불 API’로 채택하지 않고 보류한다. 최근 사건의 실제 응답·공개시점을 기관에 확인한 뒤 재평가한다. [공식 카탈로그 메타데이터](https://www.data.go.kr/catalog/3070842/openapi.json)
- D04 ASOS 시간자료와 D06 일자료는 과거 기상 분석에 사용한다. 시간별·일별 자료를 자주 내려받아도 새 분 관측이 생기지 않는다.
- D07의 단기예보·초단기실황·초단기예보는 하나의 주기로 판정할 수 없다. 초단기예보만 2순위 후보로 남기고, 단기예보는 장래 시나리오용 보조로 분리한다. 초단기실황의 선택 API 제공 간격도 별도로 확인한다.
- F06 ECMWF의 일4회 예보와 S01/S02 Sentinel 위성통과 자료는 실시간 10분 자료를 대체하지 않는다. 장래 예보와 사후 분석은 유지한다. [ECMWF 회차 안내](https://www.ecmwf.int/en/forecasts/datasets/open-data)
- G03 지형·임상·토지피복, G01 대피시설 위치, G04 기본 지도는 기본자료로 유지한다. 대피소의 **현재 개방·수용 상태**, 지도 경로의 **현재 통제 반영**은 정적 정보와 분리해서 2순위 검증한다.
- 홍수·태풍·지진·산사태 전용 11개 항목은 산불 MVP 연결 대상에서 제외하고 확장 카탈로그에 보존한다. 이 11개의 주기를 이번에 새로 실측한 것은 아니다.

구룡마을 사례는 마을 내 가건물 밀집 화재다. 산림 산불의 확산·탐지 정답으로 전환하지 않는다. 해당 FIRMS 사례의 `0행`은 기존 기간·영역 조회의 정상 필터 결과이며, 이번에 새로 측정한 산불 탐지 성능이나 갱신 속도가 아니다.

## ‘10분’을 측정하는 방법

가능하면 서비스 목표를 다음 두 항목으로 합의한다. 목표는 사용자 요구에서 제시한 600초이고, 아래 시험기간·호출 간격은 검증 방법 제안이다.

1. **주기형 관측:** 서버가 보유한 최신 실제 관측이 관측시각으로부터 600초를 넘지 않는지 본다. 평균이 아니라 초과 건수·최대 지연·누락 구간도 기록한다.
2. **사건형 경보:** 공식 발표/수정본이 만들어진 뒤 서버가 첫 수신하기까지 600초 이내인지 본다. 발효시각은 미래일 수 있으므로 공개 지연 계산의 시작점으로 쓰지 않는다. 실제 화재 발생→공식 발표 지연은 별도 항목이다.

예보는 미래의 유효시각이 있다는 이유로 최신이라고 판단하지 않는다. 발표·수정 회차의 나이와 API에서 새 버전을 첫 수신한 시각을 비교한다. 제품이 10분마다 생성되고 처리·수집에 추가 시간이 걸리면, ‘관측 후 항상10분 이내’라는 더 엄격한 목표는 실패할 수 있다.

| 기록값 | 정의 |
| --- | --- |
| observed_at | 실제 관측시각. 예보 유효시각과 구분 |
| issued_at / source_updated_at | 기관의 발표시각 / 수정시각. 둘 다 없으면 만들어 넣지 않음 |
| valid_at | 예보 유효시각·경보 효력시각 |
| first_seen_at | 동일 ID·동일 수정버전이 우리 서버에 처음 보인 시각. 반복 수집 때 덮어쓰지 않음 |
| polled_at | 매번 실제 수집한 시각. UTC와 원시간대 보존 |
| revision_or_hash | 수정 버전 또는 키를 제거한 원본 내용 해시. 같은 ID의 수정도 새 버전으로 추적 |
| issued_to_seen_sec | first_seen_at − issued_at. 주기형 자료는 observed_to_seen_sec도 계산 |
| latest age | 매 수집시각 − 최신 유효 관측시각. 미래 예보시각을 관측시각으로 쓰지 않음 |

실행 절차는 다음과 같다.

1. 키 승인·호출량을 확인하고 지점/지역·필드·원시간대·정상 오류코드·페이지 범위를 고정한다.
2. 허용 쿼터 내에서 초기 폴링을 60초로 제안한다. 하루 약1,440회/엔드포인트이고 다지점·페이지·재시도는 별도 증가하므로 실제 할당량에 맞춘다. 폴링을 10분으로 두면 제공 지연에 최대10분 대기가 더해져 목표를 넘길 수 있다.
3. AWS는 우선 24~72시간과 복수 지점으로 시험한다. 이것은 예비 검증이며 장애·재난 폭주 시 성능 보증은 아니다. 주기형 레코드 누락과 원천 결측을 분리한다.
4. 사건형 문자·특보·통제는 신규/수정/해제 표본이 필요하다. 신규 사건이 없는 기간에는 ‘지연 측정 표본 없음’으로 남긴다. 오래전에 발표된 유효 경보는 주기형 관측처럼 나이만으로 무효화하지 않는다.
5. 600초 이내 비율·p50/p95·최대값·600초 초과 건수·누락/오류/긴 폴링 공백을 함께 보고한다. 오래된 이력의 첫 다운로드는 실시간 지연 통계에서 제외하고 백필로 표시한다.
6. 짧은 시험에서 전부600초 이내여도 계약상 보증으로 승격하지 않는다. 시험 범위에서 ‘10분 충족 관측’으로만 기록하고 운영 모니터링을 이어간다. 초과한 경우 원천 공개·우리 수집·처리 단계 중 원인을 나눈다.

원천 공개시각이 없으면 최초 수신 지연은 폴링 간격만큼 불확실하다. 직전 성공 조회가 전체 범위를 빠짐없이 확인했다는 전제 아래 공개시각은 그 조회와 첫 수신 사이에 있다. `first_seen − issued_at`은 원천 지연과 우리 폴링 지연이 합쳐진 값이다. HTTP200, 응답시간100ms, RSS lastBuildDate·TTL, HTTP Last-Modified만으로 데이터가600초 안에 새로 갱신된다고 판정하지 않는다.

측정 시작 전에는 [빈 측정 양식](갱신지연_측정기록_빈양식.csv)에 임의의 지연0이나 성공 건수를 넣지 않는다. 기존 `0건`, `미수집`, `미검증` 표기도 유지한다.

## Mac 구현자에게 넘길 연결 범위

이번 재검수는 **공식 명세 재확인과 후보 선정**이다. 승인키 API 성공 응답, 실시간 원본, 24~72시간 연속 시험 결과를 새로 확보한 작업은 아니다. 무키 공개 자료는 자료 담당자가 대신 내려받아 정리할 수 있다. 키 자료는 팀이 승인받은 키를 서버 환경설정으로 제공한 뒤 수집한다. 운영 중 10분 목표를 확인하려면 구현팀 서버에서 연속 연결·저장·시간 계측이 필요하다. 모델 개발은 이 인계 범위에 포함하지 않는다.

API별 출발점은 아래와 같다. **문서에 공개된 요청 형태이며 이번에 승인키로 실행하지 않았다.** Python3 표준 라이브러리로 기존 `collect_data.py`에 별도 서브명령을 추가하거나 서버 수집기에 붙일 수 있다. 아래 표기를 그대로 호출하지 말고 시각·지점·키를 채운다. 키가 붙은 전체 URL을 로그나 Git에 저장하지 않는다.
