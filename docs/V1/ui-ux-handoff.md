# UI UX 인계와 확인 항목

팀원이 UI/UX를 준비 중입니다. 화면이 도착하면 아래 정보와 상태가 어떻게 표현되는지 맞춰보고, 그 결과로 API·모델·앱 구현 범위를 구체화합니다. 아래 화면 이름과 구성은 기능 누락을 확인하기 위한 초안이며 디자인을 확정한 것이 아닙니다.

## 화면별 필요한 정보

| 화면 또는 장면 | 사용자가 알아야 할 내용 | 필요한 데이터 |
| --- | --- | --- |
| 시작과 기본 설정 | 어떤 위치·알림·지원 정보를 사용하는지 | 권한 상태, 정보 이용 동의, 위치 사용 방식 |
| 사용자 상황 설정 | 걸을 수 있는지, 계단 이용이 어려운지, 도움이 필요한지 | 이동 제약, 준비·지원 조건, 선택한 연락 대상 |
| 현재 상황 | 지금 위치와 관련된 사건, 자료가 언제 기준인지 | 위치 정확도·시각, 사건 목록, 정보 신선도 |
| 주변 지역 사건 | 내 지역 밖 사건이 왜 관련되는지 | 사건 위치, 풍향·상류 등 관련성 근거, 확인 수준 |
| 주의와 준비 | 왜 안내하는지, 지금 필요한 행동은 무엇인지 | 평가 종류, 선택된 정책, 짧은 행동 문구, 근거 |
| 행동과 경로 | 어디로 어떻게 움직일지, 이용 가능한 길인지 | 구간·방향, 이동 제약, 위험·통제 구간, 목적지 상태 |
| 도움 요청 | 누구에게 요청하며 어디까지 진행됐는지 | 요청·전달·확인·지원 상태와 마지막 갱신 시각 |
| 정보 상세 | 공식 발표와 참고 정보, 바뀐 내용 | 출처, 발생·관측·발표 시각, 정정과 평가 변경 이유 |
| 도착과 종료 | 무엇이 확인됐고 어떤 안내가 남았는지 | 사용자 도착 응답, 사건 상태, 공식 해제 여부 |

긴급 화면에서는 행동을 먼저 이해할 수 있게 하고, 자세한 근거는 함께 확인할 수 있도록 구성하는 방안을 제안합니다. 데이터 종류와 모델명 같은 구현 정보는 사용자에게 실제 의미가 있을 때만 표시합니다.

## 상태를 혼동하지 않도록 표시할 항목

- 공식 경보와 서비스 자체의 주의·준비 안내
- 검증된 확률, 임시 위험 점수, 정보 부족으로 평가 불가
- 현재 관련 경보가 없음과 안전이 확인됨
- 알림 발송, 앱 수신, 화면 열람, 사용자의 명시적 응답
- 지원 요청 생성, 상대에게 전달, 상대가 확인, 실제 지원 진행
- 사용자의 도착 응답과 사건·재난의 공식 해제

정보 부족을 0% 또는 정상 상태로 표시하지 않습니다. 숫자 확률을 표시하는 방식은 평가 대상과 검증 결과가 정해진 뒤 결정합니다.

## 사용자 응답

기본적으로 확인, 이동 가능, 이동 어려움, 도움 필요, 도착 등 필요한 응답을 빠르게 입력할 수 있어야 한다는 설계 제안입니다. 응답은 다음 평가와 대응에 반영합니다.

음성 대화를 포함하면 STT, 발화 의도 해석, 중요한 상태 변경의 확인, 소음·오인식 시 대체 입력이 추가됩니다. 사용자가 “다리가 아프다”고 말한 경우의 임시 상태 변경과 평소 프로필 수정은 구분해야 합니다. 음성 대화의 MVP 포함 여부는 아직 정하지 않았습니다.

## 예외 상태

| 상황 | 화면과 흐름에서 정할 내용 |
| --- | --- |
| 위치 권한 거부·정확도 부족 | 위치 불확실성 표시와 허용할 대체 위치 입력 |
| 알림·음성 권한 거부 | 사용할 수 있는 전달 방식과 권한 상태 설명 |
| 통신 끊김 | 마지막 정보의 시각, 현재 갱신 불가, 저장된 안내의 한계 |
| 수집 실패·오래된 자료 | 최신 확인이 안 된 상태와 재시도 진행 |
| 출처 간 충돌·사건 정정 | 무엇이 확인·미확인인지와 안내 변경 이유 |
| 경로 탐색 실패·이용 불가 | 근거 없는 경로를 그리지 않고 해당 상황의 지원·보호 행동 표시 |
| 목적지 운영 상태 미확인 | 이용 가능성이 확인되지 않았다는 표시 |
| 사용자가 이동할 수 없음 | 지원 요청 또는 검토된 대체 행동으로 전환 |
| 보호자·지원자가 응답하지 않음 | 전달 상태와 실제 가능한 다음 연락·대응 방식 |
| 3D·음성 처리 지연 | 텍스트·기본 지도 등 준비된 안내를 먼저 제공 |
| 사용자가 응답하지 않음 | 재안내·연락 조건을 정하고 미응답을 완료로 처리하지 않음 |

배터리, 네트워크, OS 권한에 따라 제공 가능한 동작이 달라집니다. 다른 앱보다 우선하는 전체 화면과 최대 볼륨은 회의의 희망 동작이며, 목표 기기의 허용 범위와 권한 상태를 확인해 UI에 반영해야 합니다.

## 시연 확인 목록

- [ ] 같은 사건에 대해 세 가지 사용자 상황의 행동·경로가 합리적으로 달라진다.
- [ ] 현재 지역 밖에서 시작한 사건이 관련 정보를 통해 연결되는 흐름을 보여준다.
- [ ] 새 정보가 들어오면 평가와 안내가 바뀌고 변경 이유를 확인할 수 있다.
- [ ] 동일 기사 재인용을 독립적인 여러 증거처럼 표현하지 않는다.
- [ ] 긴급 공식 지시는 생성 설명과 3D 준비 완료를 기다리지 않는다.
- [ ] 이동 불가 또는 경로 없음 상황에서 다음 행동을 보여준다.
- [ ] 정보가 오래됐거나 통신이 끊긴 상태를 정상·안전으로 표시하지 않는다.
- [ ] 발송·열람·응답·지원 확인·도착을 구분한다.
- [ ] 시뮬레이션 입력과 실제 수집 정보를 구분한다.

## UI UX 수령 후 진행 순서

1. 화면을 서비스 시나리오와 연결하고 빠진 입력·상태·분기를 확인합니다.
2. 첫 재난·지역, 실내·실외, 주요 사용자, 음성 대화와 3D 범위를 결정합니다.
3. 화면에 필요한 실제 자료 샘플을 확보하고 데이터 필드·갱신·실패 계약을 정의합니다.
4. LLM 역할 제한과 임베딩·추출 보조 허용 여부를 명확히 합니다.
5. 수집·백엔드, 모델, 모바일·Unity, 검증·발표의 담당을 팀 상황에 맞춰 나눕니다.
6. 선정된 모델과 대표 입력으로 GPU 메모리·처리 지연을 측정하고 구현 일정을 정합니다.

현재 단계에서는 팀원의 화면 구성을 기다리며 문서를 기준으로 맥락을 보존합니다. 위 항목에 실제 담당자나 완료 일정을 임의로 배정하지 않습니다.
